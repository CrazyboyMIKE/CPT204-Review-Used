# Week 08 中文学习说明：Todo 系统效率优化与 Big O

本周的核心不是新增功能，而是把 Week 06 中会反复线性扫描的功能改成索引结构。索引会占用额外空间，但能显著降低查询时间。

## 1. 复杂度审计

主要方法复杂度：

| 功能 | Week 06 常见做法 | Week 08 优化后 |
|---|---:|---:|
| 通过 ID 查任务 | `O(1)` | `O(1)` |
| 按状态查任务 | `O(n)` | `O(k)` |
| 按标签查任务 | `O(n)` | `O(1 + k)` |
| 查看所有标签 | `O(u)` | `O(u)` |
| 查看标签频率 | 重建时 `O(nm)` | 维护后 `O(u)` |
| 排序标签 | `O(u log u)` | `O(u log u)` |
| 队列重复检查 | `O(q)` | `O(1)` |
| 优先队列重复检查 | `O(p)` | `O(1)` |

其中 `n` 是任务数量，`k` 是匹配结果数量，`u` 是不同标签数量，`q` 是 FIFO 队列长度，`p` 是优先队列长度，`m` 是每个任务平均标签数量。

## 2. 标签索引：`Map<String, Set<Integer>>`

`tasksByTag` 的含义是：某个标签对应哪些任务 ID。

例如：

```text
exam -> {1, 2, 5}
java -> {2, 4}
```

按标签过滤时，不需要遍历全部任务，只要：

1. 通过标签拿到 ID 集合。
2. 根据 ID 从 `taskMap` 取任务。

所以复杂度接近 `O(1 + k)`。

## 3. 增量标签统计

Week 08 不在每次显示频率时重新统计，而是在添加或删除标签时同步更新：

- `allTags`
- `tagFrequency`
- `tasksByTag`

这叫 incremental maintenance。优点是查询快；代价是写操作更复杂，且需要保证所有索引一致。

## 4. 状态索引

`tasksByCompletion` 把任务分成两个集合：

```text
false -> incomplete task ids
true  -> completed task ids
```

标记完成时，把 ID 从 `false` 集合移动到 `true` 集合。查看完成/未完成任务时，只遍历对应集合。

## 5. 队列重复检查优化

`Queue.contains(task)` 是线性时间。为了快速判断某任务是否已经在 FIFO 队列中，代码额外维护：

```java
Set<Integer> queuedTaskIds
```

优先队列也类似，使用：

```java
Set<Integer> priorityQueuedTaskIds
```

这会多占一些空间，但重复检查变成平均 `O(1)`。

## 6. 讨论题答法

如果考试问“为什么不把所有东西都建索引”，可以这样回答：

索引能加快查询，但会增加空间成本，也会让添加、删除、更新更复杂。只有高频查询或性能瓶颈明显的功能才值得建立索引。

如果问“为什么排序标签仍然是 `O(u log u)`”，答案是：主结构用 `HashSet` 保证插入和查找快；需要排序输出时临时构造 `TreeSet`，排序不可避免需要 `O(u log u)`。
